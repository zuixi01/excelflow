## 业务目标

- 同一账号允许多人分别登录、同时提交独立任务，不按账号串行执行。
- 多个运营账号同时使用时，运营人员只能访问本账号任务；管理员可查看全部任务及创建账号。
- 面向 30 个以上任务同时提交，缩短等待时间，并保持查询、保存、下载可用。
- Worker 异常退出后任务能够恢复或明确失败，避免长期停留在“处理中”。

共享账号只能追溯到账号，无法可靠区分实际操作人；本次继续使用账号作为权限和审计边界。

## 第一批：权限、会话和账号行为

对应审查问题：1、2、3、8、9。

### 1. 统一任务权限和管理员权限

主要模块：`workflow/routes.py`、`field_reconciliation_routes.py`、`api.py`、`user_routes.py` 及相关前端页面。

- 网页管理权限以已认证的 `owner/admin` 角色为准，替换旧的 `local,service` 账号 ID 白名单判断。
- 设置接口的 `can_manage_templates` 与写入接口使用相同判定，避免页面与后端权限不一致。
- 保留明确授权的服务令牌兼容行为；服务身份仍受工作空间约束。
- 字段核对列表在计数、排序和分页前按创建账号过滤，覆盖列表摘要、商户范围和搜索结果。
- 字段核对模块为管理员提供 `created_by_id`、`created_by_username`，与主工作台一致。
- 检查任务详情、结果下载、重试、取消和批量删除是否使用相同的创建者限制。
- 缺少创建者的历史任务仅管理员可访问；保留旧 `local` 创建者的显示兼容。

验收：运营 A 看不到运营 B 的列表项、业务范围、详情或文件；管理员能看到全部任务及创建账号，并能编辑字段、模板和模型配置。

### 2. 修复多窗口 CSRF 失效

主要模块：`auth_service.py`、`auth_routes.py`、`workflow/api.ts`、`auth_models.py` 和认证持久层。

- 使用与当前登录会话绑定的稳定 CSRF 令牌，重复获取或刷新页面不使其他窗口令牌失效。
- 保留会话到期、退出、禁用和密码重置后的失效校验。
- 前端合并并发获取 CSRF 的请求，使用同一个进行中的 Promise。
- 登录身份变化时清理旧缓存；对 CSRF 失效提供明确错误，避免通用自动重放造成重复提交。
- 在测试环境验证升级前会话的处理方式；若需要重新登录，在发布说明中明确告知。

验收：同浏览器 3 个标签页交替提交成功；同账号不同浏览器的会话互不影响；退出和重置密码后旧会话不能继续写入。

### 3. 修复登录限流和管理员初始化

主要模块：`auth_service.py`、`persistence.py`、`api.py`、`admin_cli.py`、部署配置。

- 登录失败计数具有明确时间窗口；生产使用 Redis 原子计数和过期时间，本地无 Redis 时使用数据库时间窗口。
- 账户锁定和来源限流分别处理，保持对外错误信息一致，并检查反向代理下来源 IP 的可信配置。
- 时间窗口结束后，正确密码可以登录；多 API 进程使用一致的限流状态。
- 将“首次创建管理员”和“显式重置密码”拆成两个操作。
- 管理员已存在时，启动过程保留其密码、状态和角色；初始化必须能处理多个 API 进程同时启动。
- 显式重置密码继续撤销该账号已有会话。

验收：达到失败阈值会临时拒绝登录，窗口结束后可恢复；重启不恢复旧密码或启用已禁用账号；并发启动只创建一个管理员。

交付门禁：先补充能复现以上问题的回归测试，再修复，运行认证、权限和前端构建检查。

## 第二批：任务执行与故障恢复

对应审查问题：4。依赖第一批的权限回归通过。

主要模块：`queueing.py`、`worker.py`、`worker_control.py`、`workflow/routes.py`、`workflow/tasks.py`、`workflow/templates.py`、数据库迁移和部署配置。

- 在业务数据库中增加可持久化的执行记录，区分等待入队、已入队、运行、成功和失败，记录执行编号、操作、业务版本、尝试次数、Worker 和租约。
- 将业务记录与待执行记录在同一事务中保存，恢复程序能补发提交后尚未成功入队的执行。
- 使用条件更新原子领取执行，接入周期心跳；现有 `WorkerControl` 需要核对实际接入情况和原子性，不能只增加字段。
- 使用唯一执行编号和稳定的队列标识去重；重试使用明确的尝试编号。
- 恢复扫描只处理待入队或租约过期的执行，不重复调度健康的排队、运行任务。
- 暂定每 30 秒续租、租约 120 秒、每 30 秒扫描，总尝试次数最多 3 次；参数通过故障测试校准。
- 只重试临时网络故障、Worker 崩溃等可恢复问题；无效文件和业务校验错误直接展示失败原因。
- 临时目录按执行编号隔离，发布结果前检查租约、执行编号和业务版本，阻止旧 Worker 覆盖新结果。
- 对齐队列超时与模型请求、Excel 解析的时间预算，分别处理可捕获异常和进程被强制终止。
- 前端能够区分等待、运行、重试和最终失败，终态停止轮询；失败任务可由有权限的账号重试。

历史“处理中”任务先与队列和 Worker 状态核对，再标记可重试；不能在升级时无条件重新执行全部任务。

验收：强制终止 Worker、重启服务、暂时中断 Redis、重复投递同一执行后，任务能恢复或明确失败；无重复导出、无数据覆盖。按暂定租约，失联检测目标为最后一次成功续租后 150 秒以内，重新执行仍受可用容量约束。

## 第三批：数据库、存储和查询性能

对应审查问题：5、6、7。依赖第二批的执行编号和版本校验约定。

### 1. 缩短数据库写事务

主要模块：`workflow/tasks.py`、`workflow/repository.py`。

- 确认映射、维护编辑和导出快照采用“读取一致版本快照、事务外计算与校验、短事务条件提交”。
- 读取多张表时保证同一版本：使用一致性事务，或读取前后核对修订号，避免混合版本数据。
- 提交时重新检查权限、状态和 `base_revision`；版本变化返回 409，不覆盖他人修改。
- 批量写入新增及变更记录，减少逐行 SQL；保留唯一性和跨字段校验语义。
- 文件写入使用独立暂存路径，提交失败时清理本次暂存文件，避免覆盖已发布结果。
- 正式并发环境使用 PostgreSQL；SQLite 保留给本地验证，缩短事务后仍按其单写入者约束评估。

验收：任务 A 的耗时计算不阻塞任务 B 的提交；同一任务同时修改时只有一个版本成功，其余返回 409。

### 2. 消除逐行重复映射

主要模块：`workflow/tasks.py`、`workflow/excel.py`、导出快照和标准化测试。

- 字段映射按任务、工作表及版本保存一次；每行保存来源工作表、行号和映射引用。
- 维护行查询仅对当前页按需补齐 `source.bindings`，保留现有接口和审计行为。现有测试确实依赖这个字段。
- 新导出快照保存公共映射及必要行数据，避免复制每行相同的定义。
- 保持旧任务和旧快照可读；先优化新写入，历史压缩作为可选的独立批处理，不在启动时全量重写。

验收：映射证据、维护回传和导出结果不变；100 个字段、1 万行的数据集不再存储 1 万份同一映射，并记录数据库大小和峰值内存的前后对比。

### 3. 实现数据库分页

主要模块：`workflow/tasks.py`、`workflow/repository.py`、数据库迁移。

- 将任务列表的账号、状态、搜索、计数和分页下推数据库，使用稳定的时间及 ID 排序。
- 为创建者和常用筛选排序增加可索引列，使用新增迁移，分批回填历史数据；创建者未知时保持管理员可见规则。
- 搜索字段在写入时统一 Unicode `casefold` 规范化，保持 SQLite 与 PostgreSQL 的搜索行为一致。
- 为工作空间、任务类型、创建账号及时间排序建立匹配查询的索引；使用真实执行计划检查效果。
- 对任务详情中的导出关联、维护行排序等相邻查询检查是否仍有全量加载，按测量结果处理。

验收：固定数据集分页无重复或遗漏，搜索计数正确；用 1 万和 10 万条任务摘要检查执行计划、返回数量和耗时，不再把全部摘要加载到 Python。

## 第四批：真实并发压测与上线

### 压测矩阵

| 场景 | 目的 |
| --- | --- |
| 同一账号，多个独立登录会话，30 / 60 个任务同时提交 | 验证共享账号不串行，任务不串数据 |
| 多个账号，合计 30 / 60 个任务同时提交 | 验证隔离及共享容量 |
| 同浏览器多个标签页交替提交 | 验证 CSRF 与登录状态 |
| 相同表头冷缓存、热缓存；不同表头冷缓存 | 区分缓存收益和实际执行容量 |
| 实际脱敏文件，以及 1 万行 × 100 列、2 万行 × 50 列样本 | 测量解析、校验、存储和导出开销 |
| 导入、维护保存、列表查询与导出混合运行 | 防止后台任务拖慢交互请求 |
| Worker 被终止、Redis 暂时不可用、模型 429 / 超时 | 验证故障恢复和重试上限 |

每份样本仍须符合当前上传、行列和单元格总量限制。性能压测使用真实 PostgreSQL、Redis、Worker；真实模型与模拟模型结果分别报告。

### 调优与验收

- 记录提交、排队、运行、总耗时的 P50/P95、每分钟完成数、CPU、内存、磁盘、锁等待、模型调用数及 429 比例。
- 先测试当前导入 4、导出 2 的配置，再按实测资源逐步调大，其他队列也计入整机资源预算。
- 模型额度按所有进程总和限制，不能把每进程并发误当成全局并发；需要时补充 Redis 全局请求准入和退避。
- 不增加按账号串行的限制；同时观察不同账号等待时间，只有测出饥饿时再引入账号间公平调度。
- 正确性门禁：零越权、零任务串数据、零重复结果发布、无永久处理中任务、无数据库锁超时报错。
- 性能门禁：在相同硬件、样本和模型条件下对比基线，提交、查询、保存保持可用，排队和总耗时改善；根据实际业务文件确定可承诺的 P95 和持续吞吐量。
- 瞬时提交超过执行槽位仍可能排队；持续到达速率超过完成速率时，需要扩容或提升模型额度。

### 发布顺序

1. 先完成独立测试环境的数据库迁移、全量后端回归、前端构建及真实基础设施故障测试。
2. 备份业务数据库与任务文件；若从 SQLite 切换 PostgreSQL，单独校验任务、记录、修订和文件引用，并保留现有用户 ID。
3. 迁移切换期间暂停新提交并排空或明确转移在途任务，避免两个数据库同时接受写入。
4. 先部署兼容旧数据的新增结构和读取逻辑，再切换新写入；启用恢复扫描前完成历史执行核对。
5. 从小批量任务验证，再执行 30 / 60 个任务压测，按报告调整 Worker 和模型容量。
6. 回滚演练包括数据库结构、执行记录和文件格式兼容性；不能只回滚镜像而忽略新格式数据。
