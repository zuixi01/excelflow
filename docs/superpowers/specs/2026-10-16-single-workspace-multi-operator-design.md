# ExcelFlow 单工作空间多运营账号设计

## 目标

ExcelFlow 保留一个业务工作空间，不再把租户作为网页产品概念；同时为多人运营提供独立账号、角色、任务配额和操作审计。管理员账号唯一，运营人员各自使用独立账号登录。所有浏览器登录仍只提交账号和密码。

## 范围

本次改造包含：

- 一个固定的 `local` 工作空间；
- 唯一管理员账号，角色为 `admin`；
- 多个独立运营账号，角色为 `operator`；
- 可选的只读账号，角色为 `viewer`；
- 管理员创建、禁用、启用、重置密码和撤销会话；
- 每个账号的并发任务数、排队任务数和上传额度；
- 任务创建者、修改者、取消者和导出者审计；
- Redis/RQ 持久队列、按任务类型分队列和多 Worker 并发；
- PostgreSQL 任务状态、幂等键、配额和审计记录；
- 对象存储输入/输出和流式上传；
- Worker 心跳、任务租约、失败重试和队列监控。

本次不包含：

- 多租户切换、租户选择或租户注册；
- OAuth、OIDC、LDAP、MFA 和公共注册；
- 自动扩缩容平台的具体实现；
- 运营人员之间的业务数据隔离；所有运营人员共享同一个工作空间。

## 身份模型

用户表保留账号、密码哈希、角色、状态、失败次数、锁定时间和登录时间。认证接口不接受或返回 `tenant_id`。数据库中为兼容现有业务表可以继续保留固定的 `local` 工作空间值，但它不进入网页表单、用户管理界面或浏览器会话响应。

角色定义：

| 角色 | 能力 |
|---|---|
| `admin` | 唯一管理员；管理运营账号、系统配置、模板、字段和所有任务 |
| `operator` | 创建和处理任务，查看工作空间任务，编辑被授权的任务，下载业务结果 |
| `viewer` | 查看任务状态和非敏感报告，不允许上传、编辑、发布或删除 |

管理员账号只能存在一个。创建第二个 `admin`、把 `operator` 升级为 `admin` 或删除管理员都必须被拒绝。管理员禁用或重置密码时，现有会话立即撤销。

## 浏览器认证

登录请求保持最小形式：

```json
{"username":"operator-a","password":"..."}
```

服务端继续使用 Argon2id 密码哈希、HttpOnly 会话 Cookie、CSRF Token、失败锁定和统一认证失败消息。会话响应返回账号、角色、过期时间和认证方式，不返回租户字段。

管理员登录后显示“运营账号管理”入口。运营人员登录后显示自己的账号和角色，不显示租户或工作空间切换入口。

## 运营账号管理

新增或调整接口：

- `GET /api/v1/operators`
- `POST /api/v1/operators`
- `PATCH /api/v1/operators/{user_id}`
- `POST /api/v1/operators/{user_id}/reset-password`
- `POST /api/v1/operators/{user_id}/disable`
- `POST /api/v1/operators/{user_id}/enable`
- `POST /api/v1/operators/{user_id}/revoke-sessions`

只有 `admin` 可以调用账号管理接口。账号响应只返回公开字段、角色、状态、配额和时间，不返回密码哈希、完整会话令牌或完整 IP。创建账号时密码只经过一次性请求进入哈希流程，不写日志。

## 配额模型

配额同时存在于工作空间和账号两个层面：

- `workspace_max_running`: 工作空间同时运行的任务数；
- `workspace_max_queued`: 工作空间最多排队任务数；
- `operator_max_running`: 单个运营账号同时运行的任务数；
- `operator_max_queued`: 单个运营账号最多排队任务数；
- `max_upload_bytes`: 单个请求上传大小；
- `daily_submit_limit`: 账号每日提交数量，可选。

默认起点：工作空间最多 8 个运行任务、最多 100 个排队任务；每个 `operator` 最多 2 个运行任务、10 个排队任务。实际数值通过压测结果调整，不能把默认值当作容量承诺。

配额预留必须在 PostgreSQL 事务中完成，使用任务状态和账号计数的条件更新，避免多 API 实例同时放行超过上限。超限返回 `429`、稳定错误码和 `Retry-After`。任务进入终态后释放运行配额；取消、失败、超时和 Worker 回收都必须释放配额。

## 任务与审计

任务元数据新增：

- `created_by_user_id`；
- `last_modified_by_user_id`；
- `cancelled_by_user_id`；
- `completed_by_worker_id`；
- `queue_name`；
- `queued_at`、`started_at`、`completed_at`；
- `attempt`、`worker_id`、`lease_expires_at`。

所有任务列表和详情继续只显示当前固定工作空间的数据，但必须返回创建者账号和安全的审计摘要。审计事件至少覆盖：创建、入队、开始、进度、取消、重试、失败、完成、下载、编辑、发布和账号管理。

幂等键从当前文件注册表迁移到数据库唯一约束，唯一范围为固定工作空间和请求键。相同键和相同指纹返回原任务；相同键不同指纹返回 409。

## 队列和并发执行

API 变成无状态入口，不在 API 进程内执行重任务。生产环境没有 Redis 时直接拒绝启动。队列按负载拆分：

- `normal`: 普通核验、标准化；
- `heavy`: 大文件、商品归一化和高内存比较；
- `network`: 需要访问外部平台接口的任务；
- `workflow`: 模板解析、字段解析和导出。

每个 RQ Worker 一次处理一个任务，通过增加 Worker 实例获得并发。调度器在入队前检查账号和工作空间配额，并在任务元数据中保存队列和优先级。基础公平策略为同一账号最多占用其配额，队列按等待时间优先；管理员任务只能在明确的系统操作中使用管理员身份，不允许运营账号冒用管理员。

Worker 必须：

- 启动任务时创建租约和心跳；
- 心跳超时后由回收器把任务重新放回队列；
- 按错误类型执行有限次数重试和指数退避；
- 任务超时后清理临时目录并释放配额；
- 把输入和产物放在对象存储，临时文件只留在 Worker 本地工作盘。

## 文件和内存路径

上传接口改为分块流式写入对象存储或受控临时文件，不再把整个上传文件读入 API 进程内存。Worker 下载自己的输入副本，输出上传完成并校验 SHA-256 后才把任务标记为完成。任务状态、对象键和校验值写入 PostgreSQL。

生产部署继续使用 PostgreSQL、Redis 和 S3/MinIO；SQLite 只允许本地单进程开发模式，不能用于多 Worker 运行。

## 容量设计

Worker 数量按压测得到的 P95 运行时计算：

```text
workers = ceil(peak_jobs_per_minute * p95_runtime_seconds / 60 / 0.7)
```

内存至少按以下公式预留：

```text
worker_memory = workers * (p95_peak_rss_delta * 2 + 512 MiB)
```

首轮生产起步规格：2 个 API 实例、4 个 `normal` Worker、2 个 `heavy` Worker、2 个 `network/workflow` Worker；PostgreSQL 4 vCPU/8 GiB；Redis 2 vCPU/4 GiB；对象存储独立持久化。该规格只作为压测起点，必须根据真实任务分布调整。

## 迁移策略

1. 保留现有管理员账号并映射为唯一 `admin`。
2. 将已有任务的创建者缺失值填充为 `admin` 或 `system`。
3. 保留现有固定 `local` 工作空间数据，不执行跨租户迁移。
4. 新增账号、配额、幂等键、任务租约和审计迁移。
5. 先在兼容模式下接受旧的内部字段，确认所有浏览器和 Worker 已更新后，再从公开 API 和前端彻底移除租户字段。

## 验收标准

- 登录页只有账号和密码；运营账号登录后显示自己的账号和角色。
- 管理员可以创建、禁用、启用、重置和撤销运营账号会话。
- 第二个管理员账号无法创建。
- 每个运营账号的运行和排队配额在多 API 实例下仍准确。
- 多个运营账号可以同时提交任务，任务不会互相覆盖。
- 至少两个 Worker 能同时处理两个任务，API 重启不会丢失已入队任务。
- Worker 崩溃、超时和重试都会回收配额并留下审计事件。
- 相同幂等键不会创建重复任务。
- 任务列表、导出和下载审计能定位到具体运营账号。
- 全量后端测试、前端构建、并发压测和故障恢复测试通过。
