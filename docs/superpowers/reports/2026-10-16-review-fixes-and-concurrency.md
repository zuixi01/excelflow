# ExcelFlow 修复与并发验收记录

日期：2026-10-16

本次按已确认的四批方案实施。第一至第三批已完成代码和针对性回归；截至 2026-10-17，第四批的本地合成样本矩阵、大文件、分页和 Worker 配置对比已完成。容量实验使用独立测试库和目录，没有发布到生产。补测数字与仍缺少的生产证据见 [容量收尾验收](2026-10-17-capacity-final.md)。

## 已实施

1. 统一管理员权限，字段核对在计数、分页前限制创建账号。管理员可见全部任务和真实创建账号，旧 `local` 创建者兼容显示为本地管理员用户名。
2. CSRF 改为会话绑定的稳定令牌，前端合并并发取令牌请求并在身份变化时清缓存。会话和 CSRF 的数据库校验通过线程池执行，避免阻塞 API 事件循环。
3. 登录失败使用共享、有过期时间的计数。管理员初始化保留已有密码、角色和禁用状态；显式密码重置撤销会话。
4. 主工作流增加数据库事务内的待执行记录、原子领取、心跳租约、恢复扫描及最多三次总尝试。失联 Worker 的旧结果不能覆盖当前执行；输出文件按尝试隔离。Redis 入队连接有明确超时，失败后由持久记录补发。
5. 确认映射、编辑和导出快照在写事务外计算、校验和写入快照，再短事务提交并校验版本。同一版本并发编辑只有一个请求成功。
6. 新标准化任务每行保存映射引用，公共映射保存在任务和导出快照中；分页接口补齐原有 `source.bindings`。旧任务、旧快照保持可读。
7. 列表筛选、计数和分页下推 SQL，补充创建者、状态和排序索引。导出及回传增加 `parent_task_id` 列和关联索引，详情与批量删除直接筛选父任务，避免每次解析其他任务的 JSON。新增迁移 `0009`、`0010`，本地旧 SQLite 文件支持增量升级。
8. Compose 增加独立恢复服务，导入、导出 Worker 分离；部署说明补齐迁移、代理来源、密码重置和数据库及文件整体回滚步骤。

持久执行和文件发布隔离覆盖标准化/SOP 导入、模板解析与学习、导出。旧比较任务补强了原子领取和心跳，但未整体改造成相同的持久待执行模型；字段核对仍使用原有投递和重试路径。这些模块不应被描述为已经具有主工作流相同的故障恢复保证。

## 验证范围

- 2026-10-16 全量后端记录：498 通过、62 跳过，JUnit 证据为 `.codex-artifacts/review-regression.xml`；后续新增的压测脚本校验另行记录。
- 真实 PostgreSQL/Redis/RQ：Worker 进程以退出码 42 异常结束后，过期恢复至第二次尝试并成功；旧执行写入被拒绝，只有一份有效来源结果。Redis 连接失败后重建调度器可补发，重复投递无重复处理。
- 真实 HTTP 模型故障：模板学习链验证 429、读取超时的重试，以及 401 凭据错误、无效草稿的终止行为。标准化字段建议保留既有降级语义：模型失败显示人工确认提示，不自动重新执行整个标准化任务。临时执行错误受三次总尝试限制。
- 数据事务：暂停任务 A 的计算不阻塞任务 B 写入；并发编辑版本冲突、旧来源字段兼容、Unicode 搜索和稳定分页通过。
- 数据迁移：旧 SQLite 升级、回填、降级保留任务；独立 PostgreSQL 空 schema 到最新版本已通过。
- 前端 `pnpm build` 通过；Playwright 检查管理员/运营、1440px/375px 视口，创建账号显示正确、无横向溢出、无页面异常。浏览器检查使用模拟接口，真实账号权限同时由后端和 HTTP 压测验证。
- 跳过项主要为未配置 .NET/LibreOffice 的渲染器合同、既有可选性能测试和其他外部基础设施测试，不能视为通过。当前工作流压测独立执行。

## 压测方法

工具：`tools/benchmark_workflow_capacity.py`。每轮创建独立 PostgreSQL schema、任务目录和合成账号，保留报告。真实 API 两个进程，导入四个、导出两个 RQ Worker；Linux 使用生产同款 `rq.worker.Worker`。每个提交使用独立登录会话。

矩阵为 30/60 任务 × 一个共享账号/四个账号 × 相同表头冷缓存/热缓存/不同表头，共 12 场景、540 个任务。样本为 100 行 × 8 列。每个任务完成上传、映射、维护保存、导出、下载，并核对独有修改值、创建账号、跨账号 404 以及一次有效执行。先运行预热任务，预热不计入矩阵。

模型为实际 HTTP 服务上的合成响应，每次固定延迟 100ms。正式容量测量没有注入模型错误，429/超时单独做故障回归。另测 10,000 行 × 100 列、20,000 行 × 50 列的上传到导出下载，及 10,000/100,000 条摘要的深分页与 PostgreSQL 执行计划。

机器为 Intel i5-10400，6 核 12 线程；Docker Desktop 可用 12 个逻辑 CPU、约 15.5 GiB 内存，后台另有既有容器。代码和测试文件使用 Windows 绑定挂载，包含挂载 I/O 开销。CPU 百分比按进程求和，100% 约为一个逻辑核；内存为 API/RQ 进程 RSS 合计峰值，未计数据库、Redis 和驱动器缓存。锁等待是间隔采样，零样本不等于从未发生任何短暂锁等待。

Windows 原生双 API 进程曾在共享监听 socket 上阻塞，试用 IOCP 后又观察到原生访问异常。相关诊断保留在 `.codex-artifacts/`，未保留未经验证的事件循环替换。生产并发结论以 Linux 结果为准；Windows 本地功能验证使用单 API 进程。

## 测量结果

此前生产同款 Worker 的部分矩阵发现详情查询瓶颈：在 884 条工作流对象上，JSON 导出关联过滤执行计划为顺序扫描，过滤掉 883 条记录；并发负载下样本耗时 173.512ms，随后 60 任务的查询 P95 达到 3.84 秒。证据保存在 `.codex-artifacts/detail-query-before.txt`，该轮 `.codex-artifacts/capacity-production-workers/report.json` 为未完成的诊断轮，不能计入正式矩阵。

父任务索引补修后的完整矩阵已完成，证据为 `.codex-artifacts/capacity-parent-index/report.json` 中的 12 个场景、540 个任务。各场景均完成导出与下载内容、创建账号、权限和有效执行次数的校验。

| 同时提交数 | 场景数 | 查询 P95（秒） | 排队 P95（秒） | 端到端 P95（秒） | 批次完成吞吐（任务/分钟） |
| --- | --- | --- | --- | --- | --- |
| 30 | 6 | 1.04–1.49 | 13.77–18.31 | 33.27–37.64 | 47.24–53.55 |
| 60 | 6 | 2.34–2.99 | 27.82–30.88 | 69.12–73.17 | 48.47–51.25 |

表中是各场景 P95 的最小值和最大值，不是合并全部请求后重新计算的 P95。排队和执行时间统计包含导入与导出执行记录；端到端从批次开始到各任务下载并校验完成。

该原始报告整体的 `completed` 仍为 `false`，不能把它描述为全部容量验收通过：矩阵之后的首份大文件虽然已生成并成功下载，但旧压测脚本错误地假设只有一行表头，导致计数断言中断。实际配置的数据从第 4 行开始，10,000 行数据对应 10,003 个物理行。2026-10-17 已将校验改为读取数据起始行并逐单元格核对，同时支持跳过已完成矩阵、单独补跑大文件和分页，并为每项完成结果保存检查点。

2026-10-17 已完成两份大文件及 1 万 / 10 万条摘要分页补测；JSON 过滤与父任务索引的同数据集查询分别约 1.261ms 和 0.061ms。该对照用于定位关联查询开销，不代表旧完整版本到新完整版本的整体加速比。后续两种 Worker 配置的 180 个任务也全部完成校验，详见收尾报告。

此前的 Windows 及 SimpleWorker 部分结果仅作诊断，不作为正式容量验收。

## 发布门禁

- 使用实际脱敏文件、实际模型额度和正式服务器复测，确定可承诺的 P95；合成模型结果不能外推真实模型耗时。
- 正式切换前备份数据库及任务文件，排空并核对旧队列。未提供生产部署目标，本次没有执行发布、迁移业务库或重启现有业务 API。
- 逐行映射节省量可以从当前样本和旧格式等价字节估算；没有同一份业务文件在旧完整版本上的数据库及内存基线，不能声称已实测旧版本整体内存下降比例。
- 同账号多人以账号为权限边界，无法辨认实际操作人。任务超过执行槽位仍会等待；持续提交速率超过完成速率时，需要增加 Worker 或模型额度。
- 大任务按字段排序仍在最多 20,000 行范围内内存排序，后续可按实际频次优化；本轮重点为列表分页和缩短写锁时间。
